## The problem

A guitar amplifier's character is signal processing: gain into a nonlinearity, then filters shaping
what the nonlinearity produced. Doing that in an FPGA rather than in analogue circuitry means every
one of those steps becomes an arithmetic decision — how many bits, where the binary point sits, what
happens on overflow — and getting any of them wrong is audible immediately.

That immediacy is what makes this a good hardware project. A wrong bit width in a memory controller
is a corner case found in simulation weeks later. A wrong bit width here is a loud click in the
headphones.

## How it works

The chain runs analogue in to digital out. Guitar signal enters through the MAX 10's on-chip ADC,
instantiated as a Qsys component; processed samples leave over **I²S** on GPIO to an external DAC.
The 50 MHz board clock is divided down to a sample rate of 48 kHz × 3.

`effects_pipeline` is where the effects chain lives, and everything inside it is fixed-point:

```system-verilog
module overdrive #(
    parameter WIDTH = 16
)(
    input  logic               clk,
    input  logic               valid_in,
    input  logic [WIDTH-1:0]   sample_in,
    output logic [WIDTH-1:0]   sample_out
);
```

The overdrive stage is the one that is finished, and it is the interesting one: a nonlinearity in
hardware needs a `tanh` that costs no multiplier array. The repository carries two answers to
that — `ovrd_tanh_clamp` and `ovrd_piecevise_clamp`, a piecewise-linear approximation whose
breakpoints are generated by `util/tanh-tests/pwl-generator.py` and emitted as
`rtl/generated/pwl_tanh.sv`.

That pattern — **compute the coefficients in Python, generate the SystemVerilog, commit both** —
repeats for the filters. `research/filter/` works out the high-pass and low-pass responses in
Jupyter, `util/filter/low_pass_generator.py` turns a response into taps, and
`rtl/generated/filters/` holds the result. The maths is done where maths is convenient, and the RTL
stays a table lookup and a multiply-accumulate.

Underneath sits a small fixed-point library — `fixed_multiply`, `signed_expand`, `sign_unsign`,
`complex_multiplier` — because the sign-extension and rounding rules are exactly where a DSP
pipeline goes quietly wrong.

## Verification

Six **cocotb** benches in `sim/cocotb/`, one per unit: `fxp_multiply`, `signed_expand`,
`piecevise_clamp`, `tanh_clamp`, `hipass_filter`, and `simulate_sound`, which runs audio through
the pipeline. Writing testbenches in Python rather than SystemVerilog is what makes the last one
practical — the reference answer is a NumPy expression, and the same script that generated the
coefficients can check the hardware that uses them.

## Where it stands

Overdrive works. The README's feature list is the honest status:

- **Done** — overdrive.
- **Not yet** — gain as a separate stage, impulse-response convolution for cabinet simulation
  (`ir_filter` and `rtl/generated/ir_weights.sv` are the groundwork), reverb, echo.

Reverb and echo both need sample memory measured in tens of milliseconds, which on this board means
deciding between on-chip block RAM and an external part. That decision, not the filter maths, is
the next real piece of work.
