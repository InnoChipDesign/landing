## The problem

A single-port SRAM serves one request per cycle. When several units in a design need memory at the
same time — two fetch units, a fetch and a writeback, a CPU and a DMA engine — the usual answers are
both bad. A true multiport SRAM costs area that grows fast with port count. Time-multiplexing one
port costs every client a stall whenever anyone else is using it.

Banking is the third answer: split the address space across several independent single-port
memories, and let requests to *different* banks proceed in parallel. Two clients collide only when
they happen to address the same bank in the same cycle. The design question is how many banks you
need before that stops being common — which is the question the
[bandwidth analysis](https://www.researchgate.net/publication/355220832_Multibank_memory_bandwidth_analysis_in_on-chip_system)
the project follows sets out to answer.

## How it works

Each port gets a decoder that inspects the address and routes the request to one bank —
`addr % banks` in the shipped configuration. An arbiter resolves the case where two ports pick the
same bank in the same cycle. Both the port count and the bank count are parameters, which is what
makes the throughput sweep possible at all.

Everything speaks **ready/valid**, so a stalled bank backpressures its port instead of dropping a
transaction. Two guarantees fall out of that, and they are the ones a client actually designs
against:

- **Bounded stalls.** When several ports are served at once the order is arbitrary, but no port
  waits more than `N_ports` cycles. Arbitrary is not the same as unbounded.
- **Constant latency after acceptance.** Once a read is accepted, the data arrives a fixed number
  of cycles later, accompanied by a ready signal. Writes commit on the same fixed delay. A client
  can pipeline against a constant; it cannot pipeline against "eventually".

The README is honest about the one place this breaks down: the read port's ready/valid handshake
carries an extra clock of delay that a more careful implementation would not need.

## Verification

The testbench is the larger half of this repository, which is the right ratio for a memory
subsystem:

- **`golden_memory_pkg`** — a behavioural model of what the memory should contain. Every
  transaction is applied to both the RTL and the model, and the two are compared.
- **Directed tests** (`0_direct_test`) — a fixed set of known-answer cases for correctness.
- **Randomised tests** (`1_randomize_test`) — every port hits random addresses every cycle, which
  is how bank conflicts get exercised at a rate no hand-written case reaches.

A conflict-free memory is easy to get right and easy to get wrong in ways directed tests never
notice. Random traffic against a golden model is what actually catches the arbiter dropping a
transaction under contention.

## Results

The throughput sweep is the deliverable: bank count against sustained bandwidth under random
traffic, which locates the point where adding banks stops buying anything. The slides in
`doc/presentation/` carry the numbers, and the paper the design follows carries the analysis.
